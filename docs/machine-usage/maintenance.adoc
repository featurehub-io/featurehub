= Maintenance Windows

The system in version 1.11 introduces 3 new variables, `maintenance.start`, `maintenance.end` and `maintenance.message`. If these are defined in the Management Repository or Party Server config,  then as long as their "end" window hasn't passed, they will show in the UI. 

NOTE: Set these in the `src/test/application.properties` file when running in the IDE, the start/end timestamps must be in UTC format e.g. `2026-08-17T10:15:30.00Z`. 

Further more, they will automatically turn into shutting down the UI for the purposes of that specific maintenance window. If the time on the client app is within that window, the DIO Interceptor in `client_api.dart` will add the maintenance window information to the `active` stream instead of the `pending` one, causing the "Scheduled Maintenance" window overlay to pop up and prevent further interaction.

== Maintenance indicators in  the UI

The way this works is that when MR/Party Server detects these environment variables are set on the server, it will add a Response Header (including to CORs) of `X-Maintenance-Start`, `X-Maintenance-End` and `X-Maintenance-Message` for every response. The DIO interceptor picks up on this and performs the appropriate checks in the `client_api.dart` to ensure the message is dropped into the right streams.

The `fh_scaffold.dart` picks up on both of these streams, showing the appropriate information. 

=== No API blocking

These windows do not prevent calls going to the application once the window is open.

Another Route was also added `maintenance` so that if the server detects a 503 with a `retry-after` header being set, it will automatically route to the maintenance page and not allow any further action.

== The maintenance responder 

This is a new application which just wires up the common web stuff, but it hosts the application (including all the Flutter app) but for API calls to `mr-api` (this is the prefix for all API calls for MR or the Party Server), it responds with CORS headers and a 503 response with the retry-after set to the `maintenance.end` variable, and the message set to the `maintenance.message`. This prevents any and all API calls, and is intended to be deployed in a Kubernetes or similar system and the routes to everything except `/features` swapped to it. It will therefore respond with the normal Flutter assets, server the website as normal but all backend requests will signal to the frontend the maintenance window is operational.

This allows sysadmins to scale this deploy up, change the ingres configuration, and when all traffic is routing to the `maintenance-responder`, shut down the Management Repository.

== The Party Server

In a situation where MR/Edge/Dacha are separate, this process works well but it does not when the Party Server or Party Server REST are being used as they are all in one
applications which are tied to the database. 

== Prepublishing State



Before MR is shut down, all caches should hold everything they might be asked for. "Publish All to Cache"
(`CacheResource.cacheRefresh` with `allTheThings`) calls `DbCacheSource.publishObjectsAssociatedWithCache()`, which
republishes every environment and service account to Dacha2 over CloudEvents.

== Redis fallback for Dacha2

If `redis.url` is set on MR, `RedisCacheFeature` (`backend/mr-eventing-redis`) registers a `RedisCacheBroadcaster`
alongside the normal broadcasters.

- Every environment, service account or feature event schedules a debounced re-read of the *whole* object from the
  database (`CacheWalker`, implemented by `DbCacheSource`), which is then written to Redis. All work for one id runs on
  the same `RedisCacheWriter` worker, so the last write for an id is the latest database state.
- It is a `SelfSyncingCacheBroadcast`: `publishObjectsAssociatedWithCache()` does not fan out to it. Instead it asks it
  to run `RedisFullSync`, which writes everything and sweeps keys that are no longer in the database (re-checking each
  one first). A full sync also runs at startup and every `redis.full-sync-interval-hours`, guarded by a Redis lock.
- On shutdown, `RedisCacheWriter` (an `ExecutorPoolDrainageSource`) finishes pending writes.

If `dacha2.redis.url` (or `redis.url`) is set on Dacha2, `Dacha2MRClientFeature` binds `Dacha2FallbackServiceClient`
in front of the MR client.

- Connection failures and 5xx responses (including the maintenance responder's 503) open a circuit, and cache misses
  are then read from Redis. MR is probed again every `dacha2.redis.mr-retry-interval-ms`.
- MR 4xx responses are authoritative. A Redis miss is a `ServiceUnavailableException`, so it never lands in the
  non-expiring miss caches.
- When the circuit closes, `Dacha2RedisRecovery` invalidates the entries that came from Redis
  (`dacha2.redis.evict-on-recovery`, default true).
- The Redis connection comes from a `RedisSource`. With `dacha2.redis.config-file` set it is a
  `ReloadingRedisSource`, which re-reads those properties files every `dacha2.redis.config-reload-seconds`. It swaps
  connections atomically, closes the old one after a grace period, and keeps the current one if the new config is
  invalid. Each request fetches the connection once. While there is none, the client passes MR failures straight
  through and the circuit never opens. That way Redis can be enabled on running Dacha2 instances, which matters
  because restarting Dacha2 empties its cache.

`dacha2` is in the maintenance responder's default `interceptPrefixes`, so if MR's address is pointed at the
responder, Dacha2 gets a 503 (fallback) rather than a 404 (which it would cache as "does not exist").

== Maintenance publish-all endpoint

`MaintenancePublishResource` (`backend/mr`, `POST /maintenance/publish-all`) is registered by the open-source MR
`Application` *only* on the separate monitoring port (`MetricsHealthRegistration.hasExternalMonitoringPort()`), never
on the main port, as it is unauthenticated.

- Its services come from the main context through `MaintenancePublisher`, either of which may be missing.
- If Redis is configured it runs `RedisFullSync.syncAll` synchronously (409 if the lock is held). It then calls
  `CacheSource.publishToStreamingCaches()`, which in `DbCacheSource` publishes to the non-self-syncing broadcasters
  without asking Redis for a second sync.
- It is meant to be called once Admin traffic is on the maintenance responder. That makes it a race-free final sync,
  which matters because incremental Redis updates are only ordered per MR process: several MRs can overwrite each
  other out of order.
- Other applications that embed MR do not register it.

The operator documentation is in `docs/modules/ROOT/pages/maintenance.adoc`.
