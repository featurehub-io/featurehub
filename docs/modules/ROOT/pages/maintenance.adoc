= Maintenance Windows

From version 1.11, FeatureHub lets you announce a planned maintenance window to Admin app users. It also provides
a dedicated *Maintenance Responder* image that holds the Admin app in maintenance mode while the Management Repository
(MR) is shut down, for example during a database upgrade.

Maintenance windows only affect the Admin app and the MR API. SDK traffic through Edge keeps working, so your
applications continue to receive features throughout.

[#_configuring_a_maintenance_window]
== Configuring a maintenance window

A maintenance window is defined by three properties. Set them the same way as any other
xref:configuration.adoc#_run_configuration[FeatureHub configuration], as environment variables or in
`/etc/app-config/application.properties`.

- `maintenance.start` - the start of the window, as an ISO-8601 UTC timestamp, for example `2026-11-08T01:00:00Z`.
- `maintenance.end` - the end of the window, in the same format.
- `maintenance.message` - the message shown to users, for example `FeatureHub is being upgraded`.

All three must be set and the timestamps must be valid, otherwise the window is ignored.

[#_announcing_maintenance]
== Announcing maintenance in the Admin app

Set the three properties on your `mr`, `party-server` or `party-server-ish` deployment and restart it.
Until `maintenance.end` has passed, every response from the server includes these headers:

- `X-Maintenance-Start`
- `X-Maintenance-End`
- `X-Maintenance-Message`

The headers are also added to the CORS exposed headers, so they work when the Admin app is served from a different
domain.

The Admin app reads these headers and behaves as follows:

- *Before the window starts:* users see a notice of the upcoming maintenance and its message.
- *During the window* (judged by the clock of the user's browser): the Admin app shows a "Scheduled Maintenance"
overlay that blocks further interaction.

NOTE: Announcing a window does not stop the server accepting API calls. A user whose clock is wrong, or a script or
xref:admin-development-kit.adoc[Admin SDK] calling the API, can still make changes during the window. To make sure
nothing writes to the database, route the Admin traffic to the Maintenance Responder (below).

It is recommended that you republish everything to the caches before shutting your Management Repositories down so
you won't suffer an outage. Do it with the <<_maintenance_publish_all,maintenance publish-all endpoint>> after the
Admin traffic has been routed to the Maintenance Responder, so nothing can change in between. Most modern container scheduling frameworks (like
Karpenter) allow you to annotate your Dacha2 containers to prevent them from moving during this process. If you
configure the <<_redis_fallback,Redis fallback>>, Dacha2 can also serve environments it has not cached yet, and
Dacha2 pods can be moved or restarted during the window.

[#_maintenance_responder]
== The Maintenance Responder

The Maintenance Responder (Docker image `featurehub/maintenance-responder`) is a small server that replaces MR
during maintenance. It:

- serves the Admin web app as normal, so users get a maintenance page instead of a connection error
- answers every API request whose path starts with `mr-api`, `saml`, `oauth` or `dacha2` with *HTTP 503 Service Unavailable*,
with the maintenance message as the body and a `Retry-After` header set to `maintenance.end`. When the Admin app
receives this, it switches to the maintenance page.
- sends the `X-Maintenance-*` headers described above
- returns `200` on `/`, so load balancers that check the root path still route traffic to it
- exposes the usual xref:configuration.adoc#_health_and_liveness_checks[health checks] and
xref:metrics.adoc[Prometheus metrics]

It never connects to the database or to NATS, Kafka or Pub/Sub.

=== Configuration

The Maintenance Responder *will not start* unless all three `maintenance.*` properties are set.

- `maintenance.start`, `maintenance.end`, `maintenance.message` - as described
<<_configuring_a_maintenance_window,above>>. Use the same values as on MR.
- `interceptPrefixes` - a comma-separated list of path prefixes that get a 503 (default `mr-api,saml,oauth,dacha2`).
- `server.port` - the HTTP port (default `8553`). Many installs set this to match MR, for example `8085`.
- `monitor.port` - the metrics and health check port (default `8701`).
- `featurehub.url-path` - set this if FeatureHub is served under a context path other than `/`, the same as on MR.

The general options listed under xref:configuration.adoc#_common_to_all_servers[Common to all servers] also apply.

[source,sh]
----
docker run -p 8085:8085 --user 999:999 \
  -e server.port=8085 \
  -e maintenance.start=2026-11-08T01:00:00Z \
  -e maintenance.end=2026-11-08T03:00:00Z \
  -e "maintenance.message=FeatureHub is being upgraded" \
  featurehub/maintenance-responder:latest
----

[#_running_maintenance]
== Running a maintenance window

This process applies to deployments where MR runs separately from Edge and Dacha
(xref:installation.adoc#_option_2a_scalable_deployment_streaming_rest_feature_updates[Option 2a] or
xref:installation.adoc#_option_2b_scalable_deployment_rest_feature_updates_only[Option 2b]), such as Kubernetes
installs using the https://github.com/featurehub-io/featurehub-helm[Helm chart].

. *Announce the window.* Set the `maintenance.*` properties on MR and roll it out. Admin users now see the upcoming
maintenance notice.
. *Deploy the Maintenance Responder* with the same `maintenance.*` values and wait until it is ready.
. *Switch the routes.* When the window starts, change your ingress or load balancer so that all Admin traffic goes to the
Maintenance Responder instead of MR. Keep SDK traffic (Edge, usually under `/features`) where it is.
. *Publish everything to the caches* with the <<_maintenance_publish_all,maintenance publish-all endpoint>>. Admin
changes can no longer reach MR at this point, so the caches and (with the <<_redis_fallback,Redis fallback>>) Redis
end up exactly matching the database. With Redis, the call returns once the Redis full sync is complete. Changes made
by SDKs through Edge are *not* stopped by the Maintenance Responder: see
<<_sdk_feature_updates,SDK feature updates during a window>>.
. *Shut down MR* once no traffic reaches it, then carry out the database work. With the Redis fallback, MR writes any
pending Redis updates before it exits.
. *Start MR* again (removing the `maintenance.*` properties, or leaving them until the end time has passed) and wait
until it is ready.
. *Switch the routes back* to MR and remove the Maintenance Responder.

On ECS and other platforms the same pattern applies: move the Admin target group or route to the Maintenance Responder
for the duration of the work.

[#_sdk_feature_updates]
=== SDK feature updates during a window

SDKs, and scripts or test automation using a service account allowed to change feature values, can update features
through *Edge* rather than the Admin API. Routing the Admin traffic to the Maintenance Responder does not stop these
requests. Edge passes them to MR over the messaging layer:

* *While MR is still running* (after the routes are switched, before it is shut down), MR applies them to the database
as normal. They happen *after* your final publish-all, so the database is not frozen. With the
<<_redis_fallback,Redis fallback>> and more than one MR instance, Redis can again hold an out-of-order version of the
affected environments.
* *While MR is shut down*, what happens depends on your messaging platform and how it is configured. The updates
may be held and applied when MR starts again (against the migrated database), or they may be lost.

If anything changes features through Edge:

* pause it for the whole window, from before you switch the routes until MR is back, and
* if you cannot, call the <<_maintenance_publish_all,maintenance publish-all endpoint>> again immediately before
shutting MR down, to make the window as small as possible.

[#_maintenance_publish_all]
=== The maintenance publish-all endpoint

MR has an endpoint on its *monitoring port* (`monitor.port`, `8701` in the examples) that republishes everything:

[source,sh]
----
kubectl port-forward <an mr pod> 8701:8701
curl -X POST http://localhost:8701/maintenance/publish-all
----

It republishes every environment and service account to Dacha2, the same as Publish All to Cache does. If the
<<_redis_fallback,Redis fallback>> is configured, it first runs a full Redis sync: everything is written, and
anything no longer in the database is removed. The call returns when that has finished, with what it did:

[source,json]
----
{
  "cachesPublished": true,
  "redisConfigured": true,
  "redis": { "environments": 120, "serviceAccounts": 45, "orphanedEnvironments": 0,
             "orphanedServiceAccounts": 0, "removedApiKeys": 0, "durationMs": 2310 }
}
----

* `409` means another Redis full sync is running (for example MR's startup sync). Wait a few seconds and call it again.
* `503` means cache publishing is not enabled on this MR.

Call it on *one* MR instance only.

The endpoint is only available when MR has a separate monitoring port (`monitor.port` set and not `0`), and it is
never added to the main port. It is not authenticated, so the monitoring port must never be exposed outside the
cluster. That is already the case for the Dacha2 API and metrics MR serves on it. It is not available in
`party-server` or `party-server-ish`.

Unlike Publish All to Cache in the Admin app, it works while the Admin traffic is routed to the Maintenance
Responder. That is the point of it: it is the last sync before MR is shut down, with nothing changing in between.

[#_redis_fallback]
=== Serving Dacha2 cache misses from Redis

Normally, when Dacha2 is asked for an environment or service account it does not have in memory, it asks MR. While
MR is shut down those requests fail, so SDKs using an API key Dacha2 has not yet seen, or any Dacha2 pod that
restarts, cannot get features until MR is back.

To avoid this, give MR and Dacha2 a Redis instance:

* *MR* writes every environment and service account to Redis, as well as publishing changes in the normal way.
Redis only stores whole environments, so when a single feature changes MR rewrites the entire environment in Redis.
This extra work is deliberate: Redis is only read while MR is unavailable.
* *Dacha2* keeps asking MR first. If MR cannot be reached or returns a 5xx error (including the Maintenance
Responder's 503), Dacha2 serves cache misses from Redis instead, and tries MR again every 10 seconds. Once MR
answers, Dacha2 drops the entries it got from Redis and reloads them from MR.
* A `404` from MR is always trusted and Redis is not consulted. Anything not found in Redis is treated as "not
available right now", so once MR is back it loads normally.

MR keeps Redis complete by running a full sync, which writes everything and removes anything that is no longer in the
database:

* when MR starts,
* every 24 hours,
* when Publish All to Cache (the cache refresh API with `allTheThings`) is used,
* when the <<_maintenance_publish_all,maintenance publish-all endpoint>> is called. That call waits for the sync to
finish.

Only one MR instance runs a full sync at a time.

*With more than one MR instance*, the incremental updates are only ordered within each instance. If two instances
rewrite the same environment or service account at almost the same moment, the older database read can land last.
Redis then holds an earlier version of that object until it next changes or the next full sync. This includes a
removed permission or a reset API key, which Dacha2 would honour while MR is down. The objects are always complete:
it is the version that can be stale. The <<_maintenance_publish_all,maintenance publish-all endpoint>>, called after
the Admin traffic has gone to the Maintenance Responder, is the fix. With nothing changing, its full sync leaves Redis
exactly matching the database just before MR stops.

Feature updates made through Edge are not stopped by the Maintenance Responder and can still arrive after that final
sync. See <<_sdk_feature_updates,SDK feature updates during a window>>.

==== MR configuration

- `redis.url` - enables the feature, for example `redis://user:password@redis:6379` or
`rediss://password@10.0.0.3:6378` (TLS). A value with no `:` before the `@` is treated as the password only.
- `redis.mode` - `standalone` (default), `sentinel` or `cluster`. For sentinel and cluster, list several
`host:port` pairs separated by commas in the URL.
- `redis.sentinel.master` - the master name, required for sentinel mode.
- `redis.username`, `redis.password` - override the values in the URL.
- `redis.tls.ca-cert` - a PEM file with the CA certificate(s) to trust for `rediss://`, if it is not a public CA.
- `redis.key-prefix` - default `featurehub`. Use a different prefix for each FeatureHub install sharing one Redis.
- `redis.connect-timeout-ms`, `redis.socket-timeout-ms` - default `2000`.
- `redis.full-sync-interval-hours` - default `24`, `0` disables the periodic sync.
- `redis.full-sync-on-startup` - default `true`.
- `redis.env-republish-debounce-ms` - default `250`. Changes to one environment within this time cause a single
rewrite.
- `redis.pool-size` - the number of Redis writer threads, default `2`.
- `redis.shutdown-drain-seconds` - how long MR waits for pending Redis writes when shutting down, default `10`.

MR only writes to Redis when it publishes cache updates (cloud events publishing is enabled).

==== Dacha2 configuration

Dacha2 reads `dacha2.redis.*` first and falls back to the `redis.*` value, so it can use different credentials from
MR. All the connection options above are supported, and the key prefix must match MR's.

- `dacha2.redis.url` (or `redis.url`) - enables the fallback.
- `dacha2.redis.mr-retry-interval-ms` - how long to wait before trying MR again, default `10000`.
- `dacha2.redis.evict-on-recovery` - drop entries that came from Redis when MR is available again, default `true`.
- `dacha2.redis.mr-connect-timeout-ms` - connect timeout for requests to MR when the fallback is on, default `2000`.
- `dacha2.redis.mr-read-timeout-ms` - read timeout for requests to MR when the fallback is on, default `15000`.
- `dacha2.redis.config-file` - a comma-separated list of properties files to read the `dacha2.redis.*` (and
`redis.*`) settings from. They are re-read while Dacha2 runs (see below). Settings in the files take precedence, and
later files win.
- `dacha2.redis.config-reload-seconds` - how often to re-read those files, default `30`.

[#_redis_without_restart]
==== Enabling the fallback on Dacha2 without a restart

Restarting Dacha2 empties its cache, so all of it has to be reloaded from MR. To avoid that, put the Dacha2 Redis
settings in files and point `dacha2.redis.config-file` at them. Running Dacha2 instances pick up changes within
`dacha2.redis.config-reload-seconds`, and new instances read the same files when they start. Adding a URL enables
the fallback, changing a setting reconnects, and removing the URL disables it again. If a change is invalid or Redis
cannot be reached, the current connection is kept and an error is logged.

In Kubernetes, mount a ConfigMap (connection settings) and a Secret (password) as volumes, for example at
`/etc/redis-config/redis.properties` and `/etc/redis-secret/redis.properties`, and set
`dacha2.redis.config-file=/etc/redis-config/redis.properties,/etc/redis-secret/redis.properties`. Kubernetes updates
mounted ConfigMaps and Secrets in running pods without restarting them, as long as:

* the volume is *not* mounted with `subPath` (those are never updated), and
* nothing in the pod template changes when the data changes (for example a checksum annotation of the ConfigMap),
otherwise the pods are restarted anyway.

The files can exist and be empty until you are ready, or not exist yet: missing files are treated as empty. With
`dacha2.redis.config-file` set, Dacha2 uses the shorter MR timeouts above even before Redis is configured.

Enable Redis on MR first (that needs a restart, which is cheap because MR holds no cache). Then wait for its full
sync to finish (`mr_redis_last_full_sync_seconds`) before adding the settings for Dacha2.

==== Redis requirements

* Set `maxmemory-policy noeviction`. An eviction policy such as `allkeys-lru` would silently remove environments.
* Redis holds your server-evaluated API keys, so protect it like the database: use authentication, TLS and network
policy. If your Redis supports ACLs, give Dacha2 a user that can only read keys starting with the prefix (for example
`+get` on `~{featurehub}:*`) and MR a read/write user for the same keys.
* Dacha2 only ever reads from Redis.

==== Metrics

- MR: `mr_redis_writes_total`, `mr_redis_write_failures_total`, `mr_redis_env_republish_queue`,
`mr_redis_last_full_sync_seconds`, `mr_redis_environments`, `mr_redis_service_accounts`,
`mr_redis_full_sync_failures`.
- Dacha2: `dacha2_redis_configured` (`1` while a Redis connection is configured), `dacha2_mr_fallback_state` (`1` while serving from Redis), `dacha2_redis_hits_total`,
`dacha2_redis_misses_total`, `dacha2_redis_errors`.

The Redis fallback does not apply to `party-server` or `party-server-ish`, where Dacha2 runs inside the same process as
MR.

=== Party Server and Party Server-ish

`party-server` and `party-server-ish` serve the Admin app, MR and Edge from a single process connected to the
database. You can still announce a window with the `maintenance.*` properties, but if you shut the container down,
SDK traffic stops as well. In these deployments the Maintenance Responder can only stand in for the Admin app; your
SDKs will be without a live FeatureHub until the server is back. See
xref:resilience.adoc[Building for Resilience] for how SDKs behave when FeatureHub is unavailable.
